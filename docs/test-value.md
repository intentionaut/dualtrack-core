# What the slow tests are worth (INT-248)

Why this exists: a pull request that touches almost any script falls back to the 27 scripts that reach
`tests/test_loop.py`, and its 236 full-loop tests (each 8 to 57 seconds) are about 90% of the suite's time. This page says
which of them guard a journey that must never break, and which are nice to have, so the pull request run can keep the
first and leave the second to the nightly run.

Seconds in the table are from `tests/durations.json` as it was before this branch (recorded under load; one loop test
alone takes about 8 seconds on an idle laptop): 247 of 1,024 tests were over 5 seconds, and all are listed. After the
re-record on this branch, 232 of 1,061 are over 5 seconds: 25 in the safety set, 80 critical by the new list, 127 nightly.

## Critical path

A test is **critical** when it guards one of these journeys:

1. Pick a bet, build, review, open the pull request.
2. A locked area stops the run (profile, criteria, stop list, deleting changes, workflow files).
3. A safety stop fires: canary, injection, git settings, secrets.
4. A red branch never ships.
5. The merge gate holds when checks change or are missing.
6. A sandbox, secret or egress boundary holds: branch code, setup commands and agents cannot escape, reach what they should not or leak a token.

Everything else is **nightly**: still run in full every night and in any non-pull-request run, skipped in pull request runs.
The slow tests already in the safety set stay critical as they are. 53 more were added from this review, 9 more were
promoted after a second read (the merge-gate re-runs, the accent file name, render failure, outside comments, strangers asking
for changes, company-mode sandbox, the check files, the printed setup token), and the two shared-run classes below are
critical whole. A second review moved 24 sandbox, secret and egress tests (the `branch_code_*`, `setup_token_*`, `test_network_*`
and source-reader containment tests) and 6 more after reading their fix commits (a BLOCKED report after a heading, no build without
budget to review it, outside comments when the reader fails, the cross-machine run stop, one owner after a lock takeover, a home
path masked in a finding) to critical.

## How the evidence column was found

For each test, `git log -L<its lines>` lists every commit that added or changed it. A commit counts as evidence when its
subject says fix, bug, hole, leak, bypass, red-team, critical, regression, escape, stricter or closes. Subjects only: the
diffs were not read one by one, and a squashed commit (for example `2df9ff5`) shows the test was added in a fix, not that it
failed first. "none found" means no such subject, with the commit that added the test. Many tests are
feature work, not bug fixes, which is why the column is mostly empty.

## Overlap

Tests with the same set-up and the same run share a run of the loop and differ only in what they read afterwards. That is
the cost that matters: 30 slow tests have a twin like this. A later section ("One run, many checks") merges the ones whose set-up is the
default. "Near-identical asserts" is two tests whose first-argument assert sets overlap by
60% or more (3 asserts or more each); only one pair showed up, and it is two different hang guards, so both stay.

## Reading the nightly column

Nightly tests with a fix commit in the evidence column are the ones to look at first, because they once caught something.
They are nightly because their journey is not one of the five above (for example, "a real image still pushes" guards
against a false stop, not a leak). Move any of them to critical by adding its id to `CRITICAL` in
`scripts/build_affected_map.py` and running it.

## How the tiers work

- `tests/affected.json` carries three lists, written by `scripts/build_affected_map.py` (edit `CRITICAL` and `NIGHTLY` there,
  run it, commit both): `safety` (existing), `critical` (new) and `nightly` (new). Safety and critical always run in a pull
  request run.
- A pull request run is `scripts/test_parallel.py --changed BASE`. When it picks tests by file it skips nightly tests. When it
  falls back to the whole suite ("mode: full": a change to `daily_loop.sh` or the test machinery, or a map it cannot work out) it runs
  every test, nightly included; the quarantined ones are still skipped. Nightly and manual runs (no `--changed`) run every test; the count check ("tests found and
  tests run differ") still holds, and `tests/test_parallel_queue.py` checks that a run with no `--changed` runs all of them.
- A test that is both critical and nightly stays in. A tag naming a test that does not exist fails
  `test_affected.RealMap.test_every_tag_names_a_real_test`, and a pull request run treats it as "cannot tell" and runs everything.

## Time budget

A pull request run fails, before running anything, when a test it would run took over 5 seconds in
`tests/durations.json` and is not critical. A test that has no recorded time is judged after the run, on its own seconds in
that run, at three times the budget (15 seconds). A recorded test is never judged on its live seconds, so a slow or different
runner (CI is a 4-CPU Linux machine; the file was recorded on a Mac) cannot fail a test that is normally quick. This was not run on CI. `test_affected.RealMap.test_every_test_over_five_seconds_is_critical_or_nightly`
makes the same check on every test in the file, whatever a pull request picks. To clear a failure: make the test faster, or tag it
(critical only if it is on a journey above), then run `python3 scripts/test_parallel.py --record` to refresh the times.
Re-recording under a different load moves tests that sit near 5 seconds across the line (the re-record on this branch pushed
four over and they had to be tagged), so record on a quiet machine, and expect the check to name any that cross.

## Flaky tests: quarantine

`tests/quarantine.json` is a list of `{"test", "file", "reason", "date", "owner"}`: the test id, its file, why it is
flaky, the date it was listed (YYYY-MM-DD) and the owner (a role, not a person's name). A listed test:

- is skipped in pull request runs and runs in the nightly run;
- is printed in every run's output ("quarantine: N flaky test(s) ... | age | owner | reason"), so the list is always in front of whoever reads the log;
- fails `tests/test_quarantine.py` once its entry is more than 14 days old, in every run (that file is in the safety set). The way out is to
  fix the test and remove the entry. Deleting a test to clear the failure is the owner's call, not the engineer's.

Nothing retries a failing test, in a pull request run or in the nightly run. A quarantine entry is the only way a test stops
being run in a pull request, and it is dated so it cannot become permanent.

## One run, many checks

17 tests each ran a whole loop of their own for the same scenario, did nothing to the checkout first, and then read a
different part of what the run left behind. They now sit in two classes that run the loop once and let each test read
it (`SharedRun` in `tests/test_loop.py`):

- `test_loop.DefaultRun`, the default run, 13 tests. Before: 13 runs, 258 recorded seconds. After: 1 run.
- `test_loop.RejectRun`, the run where the navigator asks for changes twice, 4 tests. Before: 4 runs, 91 recorded seconds. After: 1 run.

The test bodies are unchanged and so are all their assertions. `ast.dump` of every moved test is identical to the one
on `int-248-affected-tests`, with one exception: `test_opens_a_ready_pull_request_with_a_real_trail` read the origin's
`main` before its own run and compared it afterwards, so it now reads it in the class set-up, before the shared run, and
the comparison is the same one. A class that shares a run refuses any test that asks for a different run, so a test with
its own set-up has to stay in `Loop`.

Their ids changed from `test_loop.Loop.<name>` to `test_loop.DefaultRun.<name>` or `test_loop.RejectRun.<name>`; the
tables here use the new ids. Both classes are critical as a whole, because adding a test to a run that already happens is free.

One cost: the shared run happens once per test process that holds a test of the class, and the seconds the class set-up
takes are not recorded against any test (the recorded time of each of the 17 is about 0), so the runner packs them together
as if free. Counted with the recorded durations: in an unsharded run `DefaultRun` runs 3 times and `RejectRun` once; across the
4 CI shards `DefaultRun` runs 3 times in all and `RejectRun` once. Far below 17, but not exactly one. If it matters, keep a class
in one batch in `batches()` in `scripts/test_parallel.py`.

Tests with a set-up of their own (a changed profile, a bet in bets.md, a planted lock) were left alone: they differ in
what they do before the run, so they are different scenarios, not repeats. They are the next candidates if the
nightly run ever needs to be faster.

For the non-critical tests no step of the loop was faked at a seam: none of them runs in a pull request any more, and a
fake needs a contract test pinning what the faked step hands on, which does not exist yet. Left as it was.
